# why2025-app-repository

App distribution store for the **WHY2025 / DutchVMS badge** (ESP32-P4 + ESP32-C6,
BadgeVMS mini-OS). Public repo so the badge can fetch app metadata and binaries over
HTTPS without any embedded auth token.

Inspired by Nicolai's `app-repository` workflow (PR + CI checks + per-app metadata),
built primarily for WHY's **PIE-ELF** app format. An app directory may *also*
carry a Tanmatsu-launcher **AppFS** `.bin` alongside its PIE-ELF build, for
badges running the community WHY2025 port of the Tanmatsu launcher instead of
DutchVMS — see "Tanmatsu appfs co-location" below. The two formats are
unrelated binaries for two different OSes on the same hardware; an app can
ship either, both, or neither.

## Layout

One directory per app, named after its `unique_identifier`:

```
<uid>/
  <uid>.json      # the app manifest (WHY schema, same as apps/<app>/manifest.json)
  <binary_path>   # the pre-built PIE ELF, filename per the manifest's binary_path
  metadata.json   # optional: Tanmatsu appfs build (Nicolai app-repository schema)
  <executable>    # the appfs build's ESP-IDF app image, filename per metadata.json
index.json        # generated: the single list the badge polls
scripts/
  validate.py       # schema + ELF-magic validation (CI gate)
  generate_index.py # regenerates index.json from the app dirs
```

> Note: `cj_launcher` has `unique_identifier` `badgevms_launcher`, so its directory
> is `badgevms_launcher/` (directory name always matches the uid, validated in CI).

## Manifest schema (`<uid>.json`)

Exactly the WHY app manifest — `unique_identifier`, `name`, `author`, `version`,
`interpreter`, `metadata_file`, `binary_path`, `source`.

## Tanmatsu appfs co-location (`metadata.json`, optional)

Same schema as Nicolai Electronics' `app-repository`: `name`, `description`,
`version`, `author`, `license_type`, and an `application` array of
`{targets, type: "appfs", executable, revision}` entries (`targets` is a
free-form string array — `["why2025"]` for this port). The referenced
`executable` is an ESP-IDF app image (`0xe9` magic byte, not ELF) built as a
standalone appfs project, not the PIE-ELF used everywhere else in this repo —
see `why2025-apps/apps/<uid>/tanmatsu-why2025/` for the source and build
instructions. Entirely optional per app; `validate.py` only checks it when
`metadata.json` is present.

This repo distributing the appfs `.bin` doesn't by itself make it installable
through the Tanmatsu launcher's *live* repository browser (that talks to a
REST API, e.g. Nicolai's `apps.tanmatsu.cloud` — a plain GitHub file listing
doesn't speak that schema). It's the canonical build artifact for this repo's
own history/reference and for manual SD-card side-load
(`<sd card>/apps/<slug>/` + reboot); submit to Nicolai's `app-repository` too
for the in-badge repository browser to find it.

## index.json

Generated by `scripts/generate_index.py`. Each entry adds direct, auth-free download
URLs (`raw.githubusercontent.com/.../<uid>/<uid>.json` and `.../<uid>/<binary_path>`).
The badge fetches this one file, compares versions against installed apps, and pulls
any updated ELF. If an app also ships a Tanmatsu appfs build, its entry gets a
nested `"tanmatsu"` object (version, application list, metadata_url) — the
DutchVMS badge itself ignores this key, it only understands the top-level WHY
fields.

## Submitting / updating an app

Open a PR that adds or updates `<uid>/<uid>.json` + the built ELF (and, optionally,
`metadata.json` + the appfs build). CI validates the schema and that each binary
is the right format for its manifest. **CI does not rebuild app source** — this
repo distributes pre-built binaries only (source lives in `why2025-apps`),
mirroring how AppFS `.bin` submissions work upstream. On merge to `main`, CI
regenerates `index.json`.
